## 1. How delivery works

**The outbox.** Almost every server notification is a row in
`notification_deliveries`, with one row per (recipient, channel). Code enqueues rows
(`crud_notification_delivery.enqueue`, `ON CONFLICT DO NOTHING` on the globally
unique `dedupe_key`, `app/models/notification_delivery.py:98`). The worker tick
(`backend/worker_tick.py`, run about every 60 s by `worker_loop.py`) then drives each row to a
terminal state:

| Phase | Code | What it does |
| --- | --- | --- |
| `send_due_deliveries` | `app/services/notification_outbox.py:374` (tick: `worker_tick.py:111`) | Called from more than one place at once (the tick, and inline from `enqueue_and_send`/`process_overdue`), so it first claims each due row (`crud_notification_delivery.claim`, `crud/notification_delivery.py:176`): one `UPDATE` whose `WHERE` requires the row to still be due (PENDING/FAILED, `next_attempt_at` passed, not expired — the same predicate as `get_due`, `:74, 140`) and unclaimed or stale-claimed, stamped with the wall clock and committed before any provider I/O. `get_due` excludes rows with a fresh claim. Losing the claim just skips the row (`logger.info("outbox_claim_lost")`, not an error); a won row is reloaded before dispatch. **Push:** no token → REFUSED "no push token". Expo accepted → SENT (awaits a receipt). `DeviceNotRegistered` → REFUSED and the token is cleared. Anything else → backoff (`:246–309`). **SMS:** goes through `sms_opt_out.gated_send_sms` (`:330`). Opted out → REFUSED "opted_out". Accepted → SENT. Otherwise → backoff (`:312–369`). If the kind escalates, a REFUSED/EXHAUSTED row triggers escalation straight away (`:418–423`). Every terminal/backoff update clears `claimed_at`; a claim older than `CLAIM_TTL` (5 min, a crashed dispatcher) is treated as abandoned and the row becomes claimable again. |
| `derive_session_promotions` | `notification_outbox.py:669` (tick `:115`) | MISSED → ALERTED once at least one `circle_alert` row is SENT/DELIVERED (`crud/notification_delivery.py:403`). Then enqueues the owner `circle_alerted` push and the circle re-nudge. |
| `poll_expo_receipts` | `notification_outbox.py:437` (tick `:117`) | Checks SENT push rows of every receipt-tracked kind that are at least 30 s old. The receipt then decides the outcome: DELIVERED, REFUSED (dead token), or backoff. Claims don't apply: only PENDING/FAILED rows are ever claimed. |
| `expire_and_escalate` | `notification_outbox.py:568` (tick `:119`) | Flips PENDING/FAILED rows past `expires_at` to EXHAUSTED (`crud/notification_delivery.py:59–70, 288–369`). It skips a row with a fresh claim (mid-send; expiring it would escalate a message that then goes out) and rows another dispatcher holds locked; an abandoned claim is reaped once it is older than `CLAIM_TTL`. **Separately**, a SENT **push** row (channel PUSH, a receipt-tracked kind — `_RECEIPT_KINDS`) whose `sent_at` is older than `RECEIPT_WINDOW` (30 min; Expo receipts are normally available within ~15 min) and that never got a receipt is also flipped to EXHAUSTED, with `last_error="no receipt"` (`crud/notification_delivery.py:89, 345–365`). The boundary is inclusive (exactly 30 min old is reaped); 30 min is a policy choice — Expo itself keeps receipts ~24 h. The tick runs `poll_expo_receipts` before this, and the poll can't race it: every row it processes leaves SENT for DELIVERED, REFUSED, or FAILED-with-backoff, never SENT with a stale `sent_at`; and since the poll only selects SENT rows, a receipt that turns up after the reap is ignored (the row stays EXHAUSTED). A SENT **SMS** row is never expired by either sweep — Twilio may deliver hours later, and the delivery webhook, not a timeout, is the source of truth for it. An expired row of an escalating kind (`circle_alert` only — no push kind escalates today, so a reaped SENT push never actually triggers this in practice) enqueues `contact_unreachable`. |
| Inline dispatch | `enqueue_and_send` (`notification_outbox.py:154`); `process_overdue` (`app/services/session_tasks.py:219`) | Request/webhook paths enqueue and send right away for latency. The tick still owns retries. |

`build_broadcast_rows` (`notification_outbox.py:88`) writes a PUSH row only when a
recipient user id is given, and an SMS row only when a recipient phone id is given.
So a kind whose policy lists both channels can still go out on one channel at some
call sites.

**Receipts for every push.** Every outbox kind that includes PUSH sets
`track_expo_receipts=True` — no exception: the two account-holder STOP pushes
(`account_holder_unsubscribed` and `account_holder_subscription_cancelled`)
were the last direct `ExpoPushNotificationService.send_notification` callers
outside the outbox and were migrated to it 2026-09-27
(`test_push_sends_go_through_outbox.py` now allows only `_dispatch_push`). Every outbox push is sent with
`priority="high"` and no interruption level (`notification_outbox.py:267–275`).

**SMS STOP gate.** Every outbox SMS passes `gated_send_sms`
(`app/services/sms_opt_out.py:436`), which returns `error="opted_out"` when
`phone_numbers.sms_opted_out_at` is set. Direct senders outside the outbox differ:

- **Gated:** referral reward and sponsorship magic link.
- **Ungated `sms_service.send_sms`:** OTP (the mobile/web login callers pre-check `is_opted_out`), circle welcome, and the soft-stop gate.

Twilio also refuses opted-out numbers itself (error 21610, per the `gated_send_sms` docstring).

**SMS delivery receipts.** `POST /webhooks/delivery/twilio`
(`app/api/v1/endpoints/delivery_webhooks.py:71`) maps `delivered` to DELIVERED and
`failed`/`undelivered` to backoff/retry. `POST /webhooks/delivery/sns` (`:143`, fed
by a Lambda bridge) maps `SUCCESS`/`FAILURE` the same way. Both roll the linked
`Alert.status` up (`:62`). The outbound Twilio call sets no per-message
`status_callback` (`app/services/sms.py:109–111`), so whether Twilio posts receipts at
all depends on console configuration. **That is unclear from the code.** SMS
failover to AWS SNS happens inside `sms_service.send_sms` (`app/services/sms.py:160–203`).

**Dedupe keys.** The format is `{kind}:{scope_id}:{u:<user>|p:<phone>}:{channel}[:{occurrence}]`
(`notification_policy.py:231–258`). The scope is the session id for session kinds,
the owner id for cascade kinds, the plan id for `group_plan_grace`, the
subscription id for `subscription_lapse`, and the account holder's user id for
`account_holder_unsubscribed` / `account_holder_subscription_cancelled`. The unique constraint is global and
permanent, so a repeat with the same key is **never** sent again, however much
time has passed.

**Rate limiting.** The global 60 req/min per-IP limit applies to inbound HTTP, not to
outbound notifications, so it doesn't matter here.

**Frozen copy.** Push/SMS bodies and prefilled share texts were frozen pending
owner review; the 2026-09-26/27 copy-batch review (§4) lifted the freeze for
the specific strings listed there — everything else stays frozen. The
remaining markers are the `ALLOWED`/`BACKEND_ALLOWED` lists in
`backend/tests/test_vocabulary.py` (shrunk to drop the entries for strings
that changed), and the `/sub` link notes in `app/web/short_links.py:86` and
`app/web/routes_web.py:601` (that URL is frozen "forever", unrelated to the
copy review). See §4 for how the current strings compare with the Twilio A2P
registration.
